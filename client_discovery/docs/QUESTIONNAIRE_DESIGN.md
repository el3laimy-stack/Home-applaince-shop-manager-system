# التصميم وقواعد اتخاذ القرار

## نطاق الدراسة

مصدر الحقيقة نقطة الدخول الفعلية `Frontend/alikhlas_pos/lib/main.dart` ثم `v2`، وليس README أو شاشات قديمة منفصلة عن التطبيق الجاري. كتالوج القدرات يربط كل بند بملفات ورموز فعلية، ويثبت commit المصدر. تصنيف «موجودة» ليس ضمان ملاءمة سياسة كل عميل. تصنيف «يحتاج تحققًا» يُستخدم للأجهزة والمنصات التي لا يمكن إثبات قبولها من وجود مجلد بناء فقط.

الاستبيان منفصل بالكامل؛ لا يستورد Flutter ولا يفتح SQLite ولا يفحص بيانات العملاء. HTML واحد مضمّن هو أبسط توزيع يحقق التشغيل دون تثبيت؛ لا npm runtime ولا Backend ولا API ولا خدمات مدفوعة. مصدر البيانات JSON ومحرك UMD واحد في المتصفح وNode يمنع اختلاف منطق التحليل بين النسختين.

## المحاور والتدرّج

11 مرحلة: النشاط، الحجم، دورة العمل، المشكلات الفعلية، الفواتير والأجهزة، الحسابات، المخزون والخدمة، العاملون، الهاتف، المستقبل، الأولويات. 91 تعريفًا، وبعضها قالب يتم توسيعه بمعرف ثابت لكل مشكلة أو دور. الحد الأقصى سؤالان عاديان في الصفحة، وبطاقة واحدة للأسئلة المركبة. الأولويات مقسمة إلى مجموعات لا تتجاوز6 احتياجات في الصفحة، مع حفظها تحت معرف سؤال ثابت واحد. الأساسيات المستهدفة 15–20 دقيقة؛ لم يجر قياس زمن مع بشر. أمثلة التشغيل تظهر 59/84/88 سؤالًا نشطًا بحسب النشاط، بما فيها الاختيارية. بطاقات الصلاحيات التفصيلية اختيارية.

كل تعريف يحتوي `decision`: القرار الذي تخدمه الإجابة؛ لا نطلب من العميل وصف وجود ميزة نعرفها من الكود، بل ملاءمة السياسة والاستخدام والأثر. التقديرات بنطاقات عددية، وتفاصيل التقسيط/الهاتف/الخدمة تظهر حسب الحاجة.

## مصفوفة المسارات المهمة

| الشرط | المتابعة | القرار الذي يدعمه |
|---|---|---|
| تقسيط غير مستخدم | إخفاء العقد والتحصيل المفصل | عدم توسيع المحرك بلا احتياج |
| تقسيط نادر | عقد/موعد/استثناءات دون سؤال عدد الخطط | سياسة القسط أهم من الحجم الضئيل |
| تواريخ تقويمية أو استثناءات تعاقدية | قواعد مواعيد وتأخير/سداد مبكر | فصلها عن فاصل الأيام الحالي |
| اختار حتى 3 مشكلات فعلية | تكرار/أثر/عاقبة ومثال اختياري لكل واحدة | ترتيب مشاكل مدعوم بدليل، لا افتراض مشكلة |
| لا مشكلات / غير متأكد | لا بطاقات مشكلات | التصريح بعدم وجودها مختلف عن عدم معرفتها |
| أرقام تسلسلية | استخدام البيع/الضمان/المرتجع | علاقة هوية الجهاز، لا مجرد حقل نصي |
| خدمات فعلية | تدفق الطلب وبياناته | هل يلزم نظام أوامر خدمة وربط تسليم/ضمان؟ |
| مستخدم واحد | إخفاء أدوار العاملين | عدم عرض مصفوفة صلاحيات بلا سبب |
| أدوار متعددة | قيود واعتماد وبطاقة اختيارية لكل دور | تحديد العرض والتعديل والإلغاء والتصدير |
| لا استخدام هاتف | سبب مختصر وجودة الاتصال فقط | دعم سطح المكتب خيار صحيح |
| متابعة من الهاتف | الأدوار والمعلومات والتحديث والانقطاع | لوحة قراءة قد تكفي؛ لا Android كامل تلقائيًا |
| تنفيذ من الهاتف | مهام/مزامنة/تزامن عمليات/انقطاع/كاميرا | تطبيق مكمل أم كامل أم بيانات مشتركة؟ |
| أكثر من جهاز أو موقع | بيانات مشتركة أم مستقلة أم ملخص مالك | لا مساواة بين تعدد الأجهزة وضرورة خادم |
| احتياجات مستنتجة من إجابات فعلية | أولوية العميل لكل احتياج | ضروري/قريب/مرغوب/مستقبل/غير مطلوب/غير متأكد |

التعارضات المرصودة: تسجيل دون إنترنت + تحديث فوري؛ «لا تقسيط» + وسيلة تقسيط؛ «لا هاتف» + هدف هاتف؛ «متابعة فقط» + مهمة كتابة. لكل تعارض سؤال توضيح مستقل. عدم الإجابة يخفض الثقة ويبقي القرار غير محسوم. لا نزعم اكتشاف كل تعارض بشري محتمل؛ الملاحظات الحرة تحتاج مراجعة.

## التحليل والشفافية

- `clientSaid` هو نص السؤال والقيمة الأصلية وعرضها بالعربية وحالة ظهورها. `inputPreserved` يحتفظ بملف الإدخال كله. لا نعيد صياغة مثال غير موجود على لسان العميل.
- `workflowMap` خريطة مراحل موثقة بمعرفات الإجابات؛ غياب وصف مرحلة يظهر «لم يُحدد»، ولا نستنتج ترتيب عمليات لم يذكره العميل.
- `gaps` ربط الاحتياج بدليله وحالة الكود والتوافق والقرار والثقة والجهد والمخاطر والشاشة والبيانات واختبار القبول. الوظيفة الموجودة تُجرّب أولًا قبل طلب إعادة بنائها.
- الترتيب: أولوية العميل، ثم التكرار (1–4) × الأثر (1–5)، ثم الجهد للمفاضلة. القيم المجهولة لا تصبح صفرًا. عدد المستفيدين والإلحاح والمخاطر تظهر للمراجع؛ لا نُدخل نطاقات موظفين في معادلة مالية وهمية.
- جميع البدائل الخمسة للهاتف تُعرض مع التعقيد والجهد النسبي والأمان والاعتمادية والمعمارية. لوحة المالك لا تفترض مزامنة كتابة كاملة. البيانات المستقلة لا تُنشئ حاجة لخادم تلقائيًا. غياب المعلومات قد ينتج «نحتاج توضيحًا» بدل توصية مؤكدة.
- المرحلة 0 تحتوي عيوب مراجعة الكود المؤكدة، منفصلة عن أقوال العميل. الضروريات في المرحلة1؛ الإنتاجية2؛ التوسع3 عند ثبوت الحاجة؛ المستقبل4. إذا صرّح العميل أن الهاتف/المزامنة ضروري الآن، يدرج في1 مع بوابة دراسة واعتماد؛ لا يؤجل وراء تحسينات اختيارية لمجرد اسم المرحلة3.
- «غير مطلوب» لا يدخل خطة التنفيذ. الأولوية المجهولة تظل معلقة للاعتماد. التقرير لا ينفذ تعديلات ولا ينتج أسعارًا أو مواعيد تقديرية غير مستندة.

## الإصدارات والتحقق

`schemaVersion` و`questionnaireVersion` هما `1.0.0`. المعرفات الإنجليزية ثابتة ولا تتغير عند تحسين صياغة عربية. إضافة سؤال بمعرف جديد أو حقول عليا/إجابات مجهولة في1.x تُحفظ وتحذر الأداة ولا تفسرها. اختيار غير معروف لسؤال معروف يُرفض بدل تخمين معناه. **لا تغيّر معنى معرف أو قيمة اختيار قائمة داخل نفس الإصدار الرئيسي**؛ تغييرات كهذه تحتاج إصدارًا رئيسيًا وترحيلًا صريحًا مع اختبارات حفظ الأصل. الإصدار الرئيسي المختلف يُرفض ولا يستبدل الإجابات.

`schemas/*.json` للتحقق القياسي Draft2020-12. محرك runtime يطبق أيضًا حدود الأمان والحجم والتكرار والاختيارات المستقلة وشكل البطاقات وشروط الصحة المعروفة دون تنزيل مكتبة JSON Schema. الملف حتى1.5MB، النصوص وفق حدود السؤال، بنية حتى20 مستوى و500 عنصر/حقل. لا `eval`؛ مخرجات العميل DOM نصية وHTML مُهرب، وCSP يمنع الاتصالات. الإضافات المستقبلية تُحفظ عندما تكون مفاتيح/بنية آمنة؛ مفاتيح prototype الخطرة أو إصدار غير مدعوم تُرفض.

قبل ترقية مرجع المشروع: راجع نقطة الدخول والجداول والاستخدام والشاشات والاختبارات، حدّث `capabilities.json` والعيوب، ثم ابنِ الوثائق وHTML والأمثلة واختبر. اختلاف commit ملف العميل عن كتالوج القدرات يظهر تحذيرًا؛ لا يُقال إن جهازه يملك قدرات النسخة المرفقة بالضرورة.

## حدود التشغيل

localStorage في المتصفحات وسياسات الملفات ليس وسيلة نسخ احتياطي مضمونة، لذلك JSON اليدوي أساسي. لا تشفير ولا إرسال تلقائي. الصفحات الصغيرة وRTL والحقول المسماة والتركيز المرئي واستخدام لوحة المفاتيح اختُبرت في Chromium، لا يُعد ذلك تدقيق WCAG شاملًا أو قبولًا على أجهزة هاتف فعلية. سياسة Chromium في البيئة تمنع file://؛ تفاصيل الاختبار البديل والقيود موثقة في نتائج الاختبارات.
